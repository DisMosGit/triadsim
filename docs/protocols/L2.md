# L2.md

**Project:** TriadSim — Lightweight Telecom Equipment Simulator  
**Protocols:** IEEE 802.1Q (VLAN), IEEE 802.1ad (QinQ), IEEE 802.1D/w (STP/RSTP), IEEE 802.1AB (LLDP)  
**Transport:** Layer 2 Ethernet  
**Data Encoding:** YANG (`sim-l2-switching` module), SNMP MIB objects

## 1. Introduction

The Layer 2 (L2) forwarding plane of TriadSim models the behavior of a VLAN-aware bridge as defined by IEEE 802.1Q. This document describes the supported L2 features: VLAN tagging (802.1Q), stacked VLANs (QinQ, IEEE 802.1ad), the MAC forwarding database (filtering database), a simplified Spanning Tree Protocol (STP/RSTP), Link Layer Discovery Protocol (LLDP), interface counters, and the corresponding MIB objects exposed via SNMP.

TriadSim does not implement a full data-plane forwarding ASIC. Instead, it models the **management-plane state** of an L2 bridge, allowing external management systems (NMS, SDN controllers) to read and configure VLAN membership, query the MAC table, observe STP port states, and read LLDP neighbor information. VLANs, the MAC table, STP and LLDP belong to the `sim-l2-switching` module and are reachable over NETCONF and RESTCONF; SNMP exposes a subset of BRIDGE-MIB, Q-BRIDGE-MIB and IF-MIB. LLDP has no SNMP mapping.

All IEEE background in this document is reference material. The "TriadSim" statements are drawn from `internal/model/l2.go` (model and validation), `internal/l2/*.go` (domain logic), `internal/router/oid.go` (SNMP mapping) and `internal/restconf` (management-plane paths).

### 1.1. Implementation status

**Implemented** (domain in `internal/l2`, model in `internal/model/l2.go`, SNMP mapping in `internal/router/oid.go`):

- VLAN configuration: create/replace/delete VLANs and their member ports; member validation of mode (`access`/`trunk`/`hybrid`), PVID and tagging.
- QinQ (802.1ad) configuration per member port: `qinq`, `s-tag-vid` (outer S-TAG) and `c-tag-handling` (`push`/`pop`/`transparent`), with validation that the outer tag differs from the inner PVID. `Manager.TagStack` computes the inner/outer tag pair of one member port.
- MAC forwarding database: learning (`Learn`), static/permanent entries (`SetStatic`), delete and flush (`DeleteMAC`, `FlushMAC`), `max-entries` enforcement and aging.
- Simplified STP/RSTP machine (`Handle`, `advanceSTP`): link-up/link-down/BPDU inputs, the classic five phases, forward-delay timers and a simplified root election.
- LLDP: local configuration plus a table of static remote neighbours (`SetNeighbor`, `RemoveNeighbor`) whose TTL is refreshed periodically (`refreshLLDP`).
- IF-MIB counters per interface, moved by the frame simulation and the storm injector.
- Traffic simulation (`Transmit`): in-process learning, known-unicast forwarding or flooding to the VLAN member ports, discard for a VLAN the ingress port does not carry, input error for a frame above the interface MTU, and counter updates.
- Broadcast-storm injection (`Storm`) with a sliding-window rate, storm-control discards and alarm events.

**Deliberately simplified or absent:**

- No data plane and no forwarding ASIC. Frames are simulated in process and never leave it.
- No real protocol stacks: no BPDU is encoded or decoded on the wire and no LLDPDU is sent. STP reacts to `STPEvent` values passed to `Handle`; LLDP neighbours are configured, not learned.
- No CLI `l2` subcommands: the simulator binary has the single command `simulator start`.
- LLDP is not exposed over SNMP: the OID table has no LLDP-MIB objects.
- Counters only ever grow. Nothing resets them and there is no clear-counters command; see §7.4.
- MAC ages are counted in whole seconds by the periodic sweep; the stored `age` leaf is a coarse counter, not a timestamp.
- The STP root election compares `(priority, address)` and stores only `root-id` and `root-cost`. The announcing bridge's own identity is not kept, and the roles/states of the ports that did not receive the BPDU are derived from that single comparison.
- The forwarding database is keyed by MAC address alone, so the same MAC cannot appear twice even in different VLANs (`MACTable.Validate`).
- `/restconf/operations/*` answers 501, so there are no simulation RPCs; the only simulation endpoint is the storm injector (§10.6).

## 2. IEEE 802.1Q — VLAN Tagging

### 2.1. Overview

IEEE 802.1Q defines the operation of VLAN-aware Bridges that support Virtual Local Area Networks. A VLAN is a logical partition of a Layer 2 network, identified by a 12-bit VLAN Identifier (VID). The standard specifies how the MAC Service is supported by Virtual Bridged Local Area Networks, the principles of operation of those networks, and the operation of VLAN-aware Bridges, including management, protocols, and algorithms.

TriadSim models VLANs as list entries under the `sim-l2-switching:vlans` container. Each VLAN entry has an `id` (VID, 1–4094), a `name`, an optional `description`, and a set of member ports with tagging behavior.

### 2.2. VLAN Tag Format

An 802.1Q VLAN tag is inserted into the Ethernet frame header between the Source MAC Address and the EtherType/Length field. The tag header contains:

| Field | Size | Description |
|---|---|---|
| TPID | 16 bits | Tag Protocol Identifier (0x8100) |
| PCP | 3 bits | Priority Code Point (802.1p) |
| DEI | 1 bit | Drop Eligible Indicator |
| VID | 12 bits | VLAN Identifier (1–4094) |

The VLAN Identifier is a 12-bit field specifying the VLAN to which the frame belongs. All values except 0x000 and 0xFFF may be used as VLAN identifiers, allowing up to 4,094 VLANs.

### 2.3. Port VLAN Modes

Each bridge port operates in one of the following modes:

| Mode | Description |
|---|---|
| **Access** | Frames are untagged. The port is assigned to a single VLAN (PVID). |
| **Trunk** | Frames are tagged. The port carries multiple VLANs. |
| **Hybrid** | Frames may be tagged or untagged, depending on VLAN configuration. |

### 2.4. TriadSim VLAN Model

The managed objects are defined in `internal/model/l2.go`:

```go
type VLAN struct {
    ID          uint16     `path:"id" key:"true" xml:"id" json:"id"`
    Name        string     `path:"name" xml:"name" json:"name"`
    Description string     `path:"description" xml:"description,omitempty" json:"description,omitempty"`
    Ports       []VLANPort `path:"ports/port" creatable:"true" xml:"ports>port" json:"ports"`
}

type VLANPort struct {
    Port         string `path:"port" key:"true" xml:"port" json:"port"`
    Mode         string `path:"mode" xml:"mode" json:"mode"`
    PVID         uint16 `path:"pvid" xml:"pvid" json:"pvid"`
    Tagged       bool   `path:"tagged" xml:"tagged" json:"tagged"`
    QinQ         bool   `path:"qinq" xml:"qinq" json:"qinq"`
    OuterVID     uint16 `path:"s-tag-vid" xml:"s-tag-vid,omitempty" json:"s-tag-vid,omitempty"`
    CTagHandling string `path:"c-tag-handling" xml:"c-tag-handling,omitempty" json:"c-tag-handling,omitempty"`
}
```

Validation is in `model.VLAN.Validate` and `model.VLANPort.Validate`:

- `id` must be 1–4094 and `name` must not be empty.
- `mode` must be `access`, `trunk` or `hybrid`; `pvid` must be 1–4094.
- An `access` member must not be tagged.
- The QinQ fields are checked together; see §3.3.

The member list is tagged `creatable:"true"`, so NETCONF and RESTCONF may add a member the boot template does not have. VLANs themselves are also a runtime list, so a VLAN created at runtime gets its own `dot1qVlanStaticName` instance.

The `Manager` in `internal/l2/vlan.go` manages VLANs: `CreateVLAN`, `ReplaceVLAN` (members no longer listed are removed), `DeleteVLAN`, `SetMember`, `RemoveMember`, plus the readers `VLANs`, `VLAN`, `Members`, `Member` and `Accepts`. Create, replace and set-member validate before storing and report `ErrVLANNotFound`, `ErrVLANExists` or `ErrMemberNotFound`.

## 3. IEEE 802.1ad — QinQ (Provider Bridging)

### 3.1. Overview

IEEE 802.1ad (Provider Bridges) is an amendment to IEEE 802.1Q that defines the architecture and bridge protocols for stacked VLANs, commonly known as Q-in-Q or Provider Bridging. The core idea is to provide separate instances of the MAC service to multiple independent users (customers) of a Bridged Local Area Network without requiring cooperation among the users, and with a minimum of cooperation between the users and the provider of the MAC service.

In QinQ operation, two VLAN tags are added to each customer Ethernet packet: the inner VLAN tag is customer-assigned (C-TAG), and the outer VLAN tag (S-TAG) corresponds to the carrier's assignment of a tunnel in which customer traffic is carried.

### 3.2. Frame Format

```
+----------+----------+----------+----------+----------+----------+
| Dest MAC | Src MAC  | S-TAG    | C-TAG    | Type/Len | Payload  |
| (6 bytes)| (6 bytes)| (4 bytes)| (4 bytes)| (2 bytes)|          |
+----------+----------+----------+----------+----------+----------+
```

| Tag | TPID | Purpose |
|---|---|---|
| **S-TAG** (Service Tag) | 0x88A8 | Provider-assigned; identifies the service instance |
| **C-TAG** (Customer Tag) | 0x8100 | Customer-assigned; identifies the customer VLAN |

### 3.3. TriadSim QinQ Model

QinQ is a per-member-port configuration, not a separate managed object. The three fields live on `model.VLANPort` (`internal/model/l2.go`) and are written by `Manager.SetMember` (`internal/l2/vlan.go`):

| Leaf | Meaning | Validation (`VLANPort.validateQinQ`) |
|---|---|---|
| `qinq` | Push/pop an outer S-TAG on this port | — |
| `s-tag-vid` | Outer S-TAG VID | 1–4094, must differ from the inner `pvid`; requires `qinq` |
| `c-tag-handling` | C-TAG treatment | `push`, `pop` or `transparent`; requires `qinq` |

A port that does not set `qinq` must leave `s-tag-vid` at zero and `c-tag-handling` empty.

`Manager.TagStack(ctx, id, port)` returns the tag pair the model computes for a member port: the inner (C-TAG) value is the member's `pvid` when `tagged` is true and zero when the port sends the VLAN untagged; the outer (S-TAG) value is `s-tag-vid` when `qinq` is true and zero otherwise. No tag is encoded onto a real frame: there is no wire format.

### 3.4. SNMP Mapping

There is no QinQ-specific MIB support. The Q-BRIDGE-MIB portion of the OID table is limited to `dot1qVlanStaticName` (`1.3.6.1.2.1.17.7.1.4.3.1.1`, the VLAN name, indexed by VLAN id) — see §8. The `dot1qVlan` and `dot1qTp` groups, the `dot1qVlanStaticEgressPorts` bitmap and every P-BRIDGE-MIB object are **not** implemented. `s-tag-vid` and `c-tag-handling` are reachable only over NETCONF/RESTCONF.

## 4. MAC Forwarding Database (Filtering Database)

### 4.1. Overview

A MAC bridge maintains a Forwarding Database (FDB), also called the Filtering Database in IEEE 802.1D, to map destination MAC addresses to bridge ports. The bridge builds the FDB by means of a learning process, in which it associates the source MAC address of each incoming packet with the port on which the packet was received.

The FDB supports both dynamic entries (learned) and static entries (configured by management). The IEEE 802.1D standard suggests an aging parameter with a default value of 300 seconds and a range of 10.0 to 10⁶ seconds; the model enforces those bounds (`MACAgingTimeMin` = 10, `MACAgingTimeMax` = 1000000) and seeds 300.

In TriadSim the FDB is VLAN-aware: `Manager.Learn` rejects a frame whose ingress port is not a member of the frame's VLAN with `ErrMemberNotFound`. The table itself is keyed by MAC address alone, so a MAC appears at most once regardless of VLAN. A learned entry stores the *bridge port number*, which is the interface's 1-based position in the interface list, and is also its SNMP ifIndex.

### 4.2. FDB Entry Format

| Field | Description |
|---|---|
| `mac-address` | 48-bit MAC address (unicast), the list key |
| `vlan-id` | VLAN ID (0 = no VLAN) |
| `port` | Bridge port number (1-based interface index) |
| `type` | `dynamic` or `static` |
| `age` | Seconds since last activity; read-only, only meaningful for dynamic entries |
| `permanent` | A permanent entry never ages and is never overwritten by learning |

### 4.3. TriadSim MAC Table Model

```go
type MACEntry struct {
    MAC       string `path:"mac-address" key:"true" xml:"mac-address" json:"mac-address"`
    VLAN      uint16 `path:"vlan-id" xml:"vlan-id" json:"vlan-id"`
    Port      uint32 `path:"port" xml:"port" json:"port"`
    Type      string `path:"type" xml:"type" json:"type"`
    Age       uint32 `path:"age" xml:"age,omitempty" json:"age,omitempty" config:"false"`
    Permanent bool   `path:"permanent" xml:"permanent" json:"permanent"`
}

type MACTable struct {
    Entries      []MACEntry `path:"entry" creatable:"true" xml:"entry" json:"entry"`
    AgingTime    uint32     `path:"aging-time" xml:"aging-time" json:"aging-time"`
    MaxEntries   uint32     `path:"max-entries" xml:"max-entries" json:"max-entries"`
    CurrentCount uint32     `path:"current-count" xml:"current-count" json:"current-count" config:"false"`
}
```

Validation (`model.MACEntry.Validate`, `model.MACTable.Validate`):

- `mac-address` must be a 48-bit MAC address.
- `vlan-id` must be 0–4094; `type` must be `dynamic` or `static`; `port` must be greater than zero.
- A `permanent` entry must have `type` `static`.
- `aging-time` must be 10–1000000; `max-entries` must be 1–1000000.
- `current-count` must not exceed `max-entries`, and the same MAC address must not appear twice.
- The entry list is `creatable:"true"`; `age` and `current-count` are read-only state (`config:"false"`), so management cannot write them.

`Manager` operations (`internal/l2/mac.go`): `Learn`, `SetStatic`, `MACEntries`, `MACEntry`, `DeleteMAC`, `FlushMAC`, plus `BridgePort`/`PortName` to translate between interface names and bridge port numbers. Learning a full table reports `ErrTableFull`; learning an address that is already static is a no-op.

### 4.4. Aging Mechanism

The code implements a simplified aging mechanism in `Manager.age`, which runs once per `Tick` (default period 5 s, `DefaultTickInterval`):

- Each sweep reads `now` from the injected clock and computes `elapsed` as the whole seconds since the previous sweep (`now.Sub(lastAging) / time.Second`). If `elapsed` is zero the sweep does nothing.
- Every **dynamic** entry's `age` leaf advances by `elapsed`.
- An entry whose new `age` is `>= aging-time` is removed from the table and `current-count` is republished.
- **Permanent/static** entries are skipped, so they never age out.
- `Learn` restarts an existing dynamic entry's age at zero and moves it to the new ingress port; `SetStatic` stores `age` 0 and `permanent: true`.

Because the age advances in whole seconds per sweep, an entry is removed at the first sweep after it reaches `aging-time`, not at the exact instant. Entries are not timestamped; `age` is the only aging state.

### 4.5. Managing and Clearing the MAC Table

There is **no** `simulator l2 clear-mac-table` command and no clear/flush RPC: `/restconf/operations/*` answers 501. Inside the simulator, `Manager.DeleteMAC` removes one entry and `Manager.FlushMAC` removes the dynamic entries of one VLAN (or all VLANs), leaving permanent entries in place. Over the management planes the table is read as ordinary datastore data (`GET .../mac-table`) and the entry list participates in the generic NETCONF/RESTCONF create/delete operations; `age` and `current-count` stay read-only.

### 4.6. SNMP Mapping — dot1dTpFdbTable

The MAC forwarding database is exposed through the `dot1dTpFdbTable` from BRIDGE-MIB (RFC 4188), as the three columns in `internal/router/oid.go`:

| MIB Object | OID (base) | Type | Access | Value |
|---|---|---|---|---|
| `dot1dTpFdbAddress` | `1.3.6.1.2.1.17.4.3.1.1` | OctetString (6 octets) | read-only | The MAC address, from `mac-address` |
| `dot1dTpFdbPort` | `1.3.6.1.2.1.17.4.3.1.2` | Integer | read-only | The bridge port number, from `port` |
| `dot1dTpFdbStatus` | `1.3.6.1.2.1.17.4.3.1.3` | Integer | read-only | `dynamic` → learned(3), `static` → management(5) |

**Index:** the six MAC octets, e.g. entry `02:00:00:00:00:02` is `1.3.6.1.2.1.17.4.3.1.2.2.0.0.0.0.2`. The instances come from the datastore snapshot, so a MAC learned at runtime appears in the table (`internal/router/l2_oid_test.go`).

The table is read-only: writing `dot1dTpFdbStatus` (or the other two columns) is not implemented. The related writable scalar is `dot1dTpAgingTime` (`1.3.6.1.2.1.17.4.2.0`, see §8).

Example `snmpwalk`:

```bash

1.3.6.1.2.1.17.4.3.1.2.2.0.0.0.0.2 = INTEGER: 3
```

(The agent listens on the configured `snmp.port`; `configs/default.yaml` sets 1161, so the example uses 1161. Set `snmp.port: 161` to use the standard port.)

## 5. STP / RSTP (Simplified)

### 5.1. Overview

The Spanning Tree Protocol (STP, IEEE 802.1D) and its rapid variant (RSTP, IEEE 802.1w) prevent loops in bridged networks by electing a root bridge and placing redundant ports in a blocking or discarding state. RSTP is an improvement on the original STP standard, 802.1D, which allows faster convergence.

TriadSim implements a **simplified STP/RSTP state machine** that models the classic port phases and a simplified root election without executing the full BPDU exchange protocol. Configuration (protocol, bridge priority, port role/state/priority/path-cost/edge flag) is ordinary datastore data that management may write. The machine itself is driven by `STPEvent` values passed to `Manager.Handle`, and every state change is published to the EventBus (§9.2).

### 5.2. Port Roles

RSTP defines the following port roles:

| Role | Description |
|---|---|
| **Root** | The port closest to the root bridge (forwarding) |
| **Designated** | The port providing the best path to the root for a LAN segment (forwarding) |
| **Alternate** | A backup port for the root port (discarding) |
| **Backup** | A backup port for a designated port (discarding) |

TriadSim accepts all four role names in the model (`model.STPPortRole*`). The machine itself only writes `root`, `designated` and `alternate`; `backup` is accepted from configuration but never produced.

### 5.3. Port States

RSTP consolidates the five STP states (disabled, blocking, listening, learning, forwarding) into three states:

| State | Description | Learning | Forwarding |
|---|---|---|---|
| **Discarding** | Port does not forward or learn; combines STP’s disabled, blocking, and listening states | No | No |
| **Learning** | Port learns MAC addresses but does not forward | Yes | No |
| **Forwarding** | Port learns and forwards | Yes | Yes |

In TriadSim the machine has the **five classic phases** internally (`STPPhaseDisabled`, `Blocking`, `Listening`, `Learning`, `Forwarding`), but the state written to the model depends on the protocol (`stateName` in `internal/l2/stp.go`):

- `protocol = "stp"`: the model stores `disabled`, `blocking`, `listening`, `learning` or `forwarding`.
- `protocol = "rstp"`: the model stores only `discarding`, `learning` or `forwarding`; `disabled`, `blocking` and `listening` are all written as `discarding`.

Validation accepts exactly the vocabulary of the configured protocol: `model.STPPortStates(protocol)` (`internal/model/l2.go`). A `rstp` port carrying `blocking` is rejected as an invalid value.

### 5.4. TriadSim STP Model

```go
type STPState struct {
    Enabled        bool      `path:"enabled" xml:"enabled" json:"enabled"`
    Protocol       string    `path:"protocol" xml:"protocol" json:"protocol"`                 // "stp", "rstp"
    BridgePriority uint16    `path:"bridge-priority" xml:"bridge-priority" json:"bridge-priority"`
    BridgeAddress  string    `path:"bridge-address" xml:"bridge-address,omitempty" json:"bridge-address,omitempty"`
    RootID         string    `path:"root-id" xml:"root-id,omitempty" json:"root-id,omitempty" config:"false"`
    RootCost       uint32    `path:"root-cost" xml:"root-cost" json:"root-cost" config:"false"`
    Ports          []STPPort `path:"ports/port" xml:"ports>port" json:"ports"`
}

type STPPort struct {
    Port     string `path:"port" key:"true" xml:"port" json:"port"`
    Role     string `path:"role" xml:"role" json:"role"`
    State    string `path:"state" xml:"state" json:"state"`
    Priority uint8  `path:"priority" xml:"priority" json:"priority"`
    PathCost uint32 `path:"path-cost" xml:"path-cost" json:"path-cost"`
    EdgePort bool   `path:"edge-port" xml:"edge-port" json:"edge-port"`
}
```

Validation (`model.STPState.Validate`, `model.STPPort.Validate`):

- `protocol` must be `stp` or `rstp`.
- `bridge-priority` must be 0–61440 in steps of 4096; port `priority` must be 0–240 in steps of 16.
- `bridge-address` and `root-id`, when present, must be MAC addresses.
- When STP is enabled, every port must have a known role and a state from the protocol's vocabulary. `root-id` and `root-cost` are read-only state; the rest of the port data is configuration.

The STP port list is a closed list: NETCONF/RESTCONF cannot add a port that the boot template does not contain.

### 5.5. Simulated State Transitions

The machine understands three inputs (`STPEventKind`), applied with `Manager.Handle(ctx, STPEvent{Kind, Port, RootID, RootPriority, PathCost})`:

| Input | Effect on the port |
|---|---|
| `link-up` | Role `designated`; phase `blocking`, or straight to `forwarding` when the port is an edge port |
| `link-down` | Role `alternate`, phase `disabled` |
| `bpdu` | Runs the simplified root election described below |

`Handle` returns `ErrSTPDisabled` when `enabled` is false and `ErrPortUnknown` for a port that is not in the STP state.

**Forward delays.** When a port enters `blocking` or `listening`, the machine schedules `learning` one forward delay later; entering `learning` schedules `forwarding` one more delay later. The delays are scheduled on the injected clock and applied by the periodic `advanceSTP` step, so a port walks `blocking → learning → forwarding` through two delays (default 15 s each, `DefaultForwardDelay`). `forwarding` and `disabled` cancel a pending timer. This is the classic STP walk; for `rstp` the intermediate `blocking`/`listening` phases are written to the model as `discarding`.

**Root election.** On a `bpdu` the received `(RootPriority, RootID)` is compared against the local `(BridgePriority, BridgeAddress)`. If the received bridge identifier is lower, this bridge becomes a non-root bridge: the receiving port becomes the `root` port and stores `root-cost = PathCost + port path-cost`; every other port becomes `alternate`/`blocking`. Otherwise the local bridge stays root: the receiving port stays `designated`/`forwarding` and the other ports are `designated`/`forwarding`. Only `root-id` and `root-cost` are written; the announcing bridge's own identity is not stored. Under `rstp` a root port goes to `forwarding` immediately, while under classic `stp` it starts at `blocking` and walks the forward delays.

### 5.6. SNMP Mapping — BRIDGE-MIB (bridge identity and dot1dStp)

The bridge identity and the `dot1dStp` subtree are exposed from the seeded model as follows (`internal/router/oid.go`):

| MIB Object | OID (base) | Type | Access | TriadSim source |
|---|---|---|---|---|
| `dot1dBaseBridgeAddress` | `1.3.6.1.2.1.17.1.1` | OctetString (6 octets) | read-only | `stp/state/bridge-address` |
| `dot1dStpPriority` | `1.3.6.1.2.1.17.2.2` | Integer | read-write | `stp/state/bridge-priority` |
| `dot1dStpPortPriority` | `1.3.6.1.2.1.17.2.15.1.2` | Integer | read-write | port `priority` |
| `dot1dStpPortState` | `1.3.6.1.2.1.17.2.15.1.3` | Integer | read-only | port `state` |
| `dot1dStpPortEnable` | `1.3.6.1.2.1.17.2.15.1.4` | Integer | read-only | derived from port `state` |
| `dot1dStpPortPathCost` | `1.3.6.1.2.1.17.2.15.1.5` | Integer | read-write | port `path-cost` |

**Index:** `dot1dStpPortTable` is indexed by the bridge port number, which is the 1-based interface index (with the seed of §9.3: radio0 = 1, eth0 = 2, eth1 = 3). The test `internal/router/l2_oid_test.go` reads `...17.2.15.1.3.2` for eth0.

Value mappings:

| Model value | `dot1dStpPortState` | `dot1dStpPortEnable` |
|---|---|---|
| `disabled` | `1` (disabled) | `2` (disabled) |
| `blocking` / `discarding` | `2` (blocking) | `1` (enabled) |
| `listening` | `3` (listening) | `1` (enabled) |
| `learning` | `4` (learning) | `1` (enabled) |
| `forwarding` | `5` (forwarding) | `1` (enabled) |

An unknown state is reported as `1` (disabled). Note that the RSTP `discarding` state is reported as `blocking(2)`, because BRIDGE-MIB has no discarding value.

The following BRIDGE-MIB objects are **not** implemented: `dot1dStpProtocolSpecification`, `dot1dStpBridgeAddress`, `dot1dStpPortRole`, `dot1dStpPortDesignatedRoot`, `dot1dStpRootCost`, `dot1dStpRootPort`, `dot1dStpTimeSinceTopologyChange`, `dot1dStpTopChanges` and `dot1dBaseNumPorts`.

## 6. LLDP (IEEE 802.1AB)

### 6.1. Overview

The Link Layer Discovery Protocol (LLDP), specified in IEEE 802.1AB, allows stations attached to an IEEE 802 LAN to advertise their identity, capabilities, and neighbors to other stations on the same LAN. LLDP is a one-way protocol: stations transmit LLDP Data Units (LLDPDUs) periodically and do not solicit responses.

TriadSim implements LLDP as a **management-plane model**: it maintains a local LLDP configuration and a table of remote neighbours, but does not generate or parse LLDP frames on the wire. Neighbours are configured through the management planes (`Manager.SetNeighbor`, `RemoveNeighbor`) and their `ttl` is refreshed periodically by `Manager.refreshLLDP`.

### 6.2. LLDPDU Structure

An LLDPDU consists of a sequence of Type-Length-Value (TLV) elements. Mandatory TLVs include:

| TLV | Type | Description |
|---|---|---|
| **Chassis ID** | 1 | Identifier of the chassis (MAC, IP, etc.) |
| **Port ID** | 2 | Identifier of the port |
| **Time To Live** | 3 | TTL in seconds (default 120) |
| **Port Description** | 4 | Description of the port |
| **System Name** | 5 | Assigned name of the system |
| **System Description** | 6 | Description of the system |
| **System Capabilities** | 7 | Bridge, router, repeater, etc. |

None of these TLVs is encoded or transmitted by TriadSim.

### 6.3. TriadSim LLDP Model

```go
type LLDPConfig struct {
    Enabled           bool           `path:"enabled" xml:"enabled" json:"enabled"`
    TxInterval        uint32         `path:"tx-interval" xml:"tx-interval" json:"tx-interval"`
    TxHoldMultiplier  uint32         `path:"tx-hold-multiplier" xml:"tx-hold-multiplier" json:"tx-hold-multiplier"`
    ReinitDelay       uint32         `path:"reinit-delay" xml:"reinit-delay" json:"reinit-delay"`
    TxDelay           uint32         `path:"tx-delay" xml:"tx-delay" json:"tx-delay"`
    ChassisID         string         `path:"chassis-id" xml:"chassis-id" json:"chassis-id"`
    SystemName        string         `path:"system-name" xml:"system-name" json:"system-name"`
    SystemDescription string         `path:"system-description" xml:"system-description,omitempty" json:"system-description,omitempty"`
    Neighbors         []LLDPNeighbor `path:"neighbors/neighbor" creatable:"true" xml:"neighbors>neighbor" json:"neighbors"`
}

type LLDPNeighbor struct {
    Port              string `path:"port" key:"true" xml:"port" json:"port"`
    ChassisID         string `path:"chassis-id" xml:"chassis-id" json:"chassis-id"`
    PortID            string `path:"port-id" xml:"port-id" json:"port-id"`
    SystemName        string `path:"system-name" xml:"system-name,omitempty" json:"system-name,omitempty"`
    SystemDescription string `path:"system-description" xml:"system-description,omitempty" json:"system-description,omitempty"`
    TTL               uint32 `path:"ttl" xml:"ttl" json:"ttl"`
    Capabilities      string `path:"capabilities" xml:"capabilities,omitempty" json:"capabilities,omitempty"`
}
```

Validation (`model.LLDPConfig.Validate`, `model.LLDPNeighbor.Validate`):

- `tx-interval` 1–3600, `tx-hold-multiplier` 2–10, `reinit-delay` 1–10, `tx-delay` 1–10.
- `chassis-id` must not be empty.
- A neighbour needs a non-empty `chassis-id` and `port-id` and a `ttl` of 1–65535; a port may have at most one neighbour.

**Periodic TTL refresh.** Every `Tick`, `Manager.refreshLLDP` recomputes `ttl = tx-interval * tx-hold-multiplier` and writes it to every neighbour whose `ttl` differs. It does nothing when LLDP is disabled, when there are no neighbours, or when the product is zero or above `LLDPTTLMax` (65535). This models a peer that keeps announcing itself: the neighbour stays in the table as long as the sweep can refresh its TTL; nothing removes a neighbour automatically.

### 6.4. SNMP Mapping — LLDP-MIB

LLDP is **not** exposed over SNMP. `internal/router/oid.go` contains no LLDP-MIB rule, so none of the standard objects — `lldpMessageTxInterval` (`1.0.8802.1.1.2.1.1.1`), `lldpMessageTxHoldMultiplier` (`1.0.8802.1.1.2.1.1.2`), `lldpLocChassisId` (`1.0.8802.1.1.2.1.3.2`), `lldpLocSysName` (`1.0.8802.1.1.2.1.3.4`), `lldpRemTable` (`1.0.8802.1.1.2.1.4.1`) and its columns — can be read or written through the agent. Read LLDP over NETCONF/RESTCONF instead (§10.4).

## 7. Interface Counters

### 7.1. Overview

TriadSim maintains per-interface counters as defined in the IF-MIB (RFC 2863). Every counter is read-only state (`config:"false"`) and is only ever incremented; no code path resets one. RFC 2863 defines counter discontinuities signalled by `ifCounterDiscontinuityTime`; that object is not implemented here.

### 7.2. Supported Counters

The ifTable columns and their 64-bit ifXTable counterparts come from `internal/router/oid.go`:

| Counter | MIB Object | Type | Description |
|---|---|---|---|
| `ifInOctets` | `1.3.6.1.2.1.2.2.1.10` | Counter32 | Total octets received |
| `ifInUcastPkts` | `1.3.6.1.2.1.2.2.1.11` | Counter32 | Unicast packets received |
| `ifInDiscards` | `1.3.6.1.2.1.2.2.1.13` | Counter32 | Inbound discards |
| `ifInErrors` | `1.3.6.1.2.1.2.2.1.14` | Counter32 | Inbound errors |
| `ifOutOctets` | `1.3.6.1.2.1.2.2.1.16` | Counter32 | Total octets transmitted |
| `ifOutUcastPkts` | `1.3.6.1.2.1.2.2.1.17` | Counter32 | Unicast packets transmitted |
| `ifOutDiscards` | `1.3.6.1.2.1.2.2.1.19` | Counter32 | Outbound discards |
| `ifOutErrors` | `1.3.6.1.2.1.2.2.1.20` | Counter32 | Outbound errors |
| `ifHCInOctets` | `1.3.6.1.2.1.31.1.1.1.6` | Counter64 | 64-bit high-capacity octets in |
| `ifHCInUcastPkts` | `1.3.6.1.2.1.31.1.1.1.7` | Counter64 | 64-bit high-capacity unicast packets in |
| `ifHCOutOctets` | `1.3.6.1.2.1.31.1.1.1.10` | Counter64 | 64-bit high-capacity octets out |
| `ifHCOutUcastPkts` | `1.3.6.1.2.1.31.1.1.1.11` | Counter64 | 64-bit high-capacity unicast packets out |

The ifTable and ifXTable are indexed by `ifIndex`, the 1-based interface index (radio0 = 1, eth0 = 2, eth1 = 3 in the seed). The other interface objects exposed by the same table are listed in §8.

### 7.3. TriadSim Counter Model

The model stores all eight counters on every interface (`internal/model/l2.go`); there are no separate 64-bit storage fields — the ifXTable columns expose the same values as Counter64:

```go
type InterfaceCounters struct {
    InOctets     uint64 `path:"in-octets" xml:"in-octets" json:"in-octets" config:"false"`
    OutOctets    uint64 `path:"out-octets" xml:"out-octets" json:"out-octets" config:"false"`
    InUcastPkts  uint64 `path:"in-ucast-pkts" xml:"in-ucast-pkts" json:"in-ucast-pkts" config:"false"`
    OutUcastPkts uint64 `path:"out-ucast-pkts" xml:"out-ucast-pkts" json:"out-ucast-pkts" config:"false"`
    InErrors     uint32 `path:"in-errors" xml:"in-errors" json:"in-errors" config:"false"`
    OutErrors    uint32 `path:"out-errors" xml:"out-errors" json:"out-errors" config:"false"`
    InDiscards   uint32 `path:"in-discards" xml:"in-discards" json:"in-discards" config:"false"`
    OutDiscards  uint32 `path:"out-discards" xml:"out-discards" json:"out-discards" config:"false"`
}
```

Who moves them (`internal/l2/counters.go`, `storm.go`):

- `Transmit` adds `in-octets`/`in-ucast-pkts` on the ingress port, and `out-octets`/`out-ucast-pkts` on every egress port. A frame for a VLAN the port does not carry adds one `in-discards`; a frame larger than the interface MTU adds one `in-errors`.
- `Storm` adds `in-octets`/`in-ucast-pkts` for the accepted frames, `in-discards` for the frames storm control dropped, and `out-octets`/`out-ucast-pkts` on the other member ports.
- `Increment` is the general entry point and adds any caller-supplied delta to all eight counters.

### 7.4. Counter Reset

Counters are **never reset**. `Manager.increment` writes the component-wise sum of the stored value and a delta, and nothing else writes a counter. Consequences:

- There is no clear-counters CLI command and no RESTCONF/NETCONF RPC; `/restconf/operations/*` answers 501.
- The counters are read-only state (`config:"false"`), so a management write to them is rejected, and there is no `ifCounterDiscontinuityTime` object to signal a wrap or reset.
- The values only grow for the life of the process; the seeded device starts them at zero.

## 9. Simulator Implementation

### 9.1. Go Package Structure

```
internal/l2/
├── doc.go       # package documentation
├── l2.go        # Manager, Deps, New, Run/Tick, event publishing
├── vlan.go      # VLAN and member management
├── mac.go       # forwarding database, learning, aging
├── stp.go       # simplified STP/RSTP machine and root election
├── lldp.go      # LLDP configuration and neighbour table
├── counters.go  # frame simulation (Transmit) and counters
└── storm.go     # broadcast-storm injection and alarms
```

The SNMP MIB mapping is **not** in this package: it lives in `internal/router/oid.go` (`objectRules`, the single OID table applied to the model template by `buildObjects`). The managed objects and their `Validate()` rules live in `internal/model/l2.go`.

`l2.Deps` is what the manager needs from the rest of the simulator:

```go
type Deps struct {
    Router            *router.Router  // required; path-to-model mapping
    Bus               *event.Bus      // nil swallows events
    Clock             clock.Clock     // nil uses clock.RealClock
    TickInterval      time.Duration   // zero uses DefaultTickInterval (5 s)
    ForwardDelay      time.Duration   // zero uses DefaultForwardDelay (15 s)
    StormThresholdPPS uint32          // zero uses DefaultStormThresholdPPS (1000)
    StormWindow       time.Duration   // zero uses DefaultStormWindow (1 s)
}
```

`New` fills every zero value with its default and fails only when `Router` is nil.

**Datastore use.** Configuration is written to the running datastore with `Router.Set` (the way a management plane writes it). Learned and measured state — the MAC `age` and `current-count`, the STP `root-id`/`root-cost` and port role/state, and all interface counters — goes through `Router.SetState`, which writes running and keeps candidate in step.

**Periodic work.** `Manager.Run(ctx)` loops on the injected clock and calls `Tick` every `TickInterval`. `Tick` runs three steps under one mutex and joins their errors:

- `age` — the MAC aging sweep (§4.4).
- `advanceSTP` — applies the STP phase changes whose forward delay has elapsed (§5.5).
- `refreshLLDP` — the periodic LLDP TTL refresh (§6.3).

The default tick is 5 s (`DefaultTickInterval`) and the default forward delay is 15 s (`DefaultForwardDelay`). `internal/cli/start.go` wires the manager with only `Router`, `Bus` and a real clock, so a normally started simulator uses those defaults and runs `Run` in its own goroutine.

### 9.2. Event Integration

The L2 domain publishes exactly two kinds of event through `Manager.publish`; a nil `Bus` swallows them. Timestamps come from the injected clock.

| Event | Resource | Severity | Message |
|---|---|---|---|
| `event.TypeStateTransition` | `l2/stp/<port>` | `""` | `stp <port>: <from> -> <to> (<reason>)` |
| `event.TypeAlarmRaised` | `l2/storm/<port>` | `major` | `broadcast storm on <port>: <rate> pps above the <threshold> pps limit` |
| `event.TypeAlarmCleared` | `l2/storm/<port>` | `cleared` | `broadcast storm on <port> cleared: <rate> pps within the <threshold> pps limit` |

State transitions are published by `Manager.transition` for every role/state change. `<from>` is the port state before the change (empty when the port had no state yet) and `<reason>` is one of `link up`, `link down`, `root election`, `bpdu from <root-id>` or `forward delay`. The storm alarm is published once per crossing: `TypeAlarmRaised` on the first injection above the threshold and `TypeAlarmCleared` on the first injection back within it; further injections in the same state publish nothing.

There is no `VLANCreated`/`MACLearned`/`LLDPNeighborAdded` event: VLAN, MAC-table and LLDP changes are datastore writes and produce no L2 event.

### 9.3. Configuration Example


An invalid write is rejected by the model with `422 Unprocessable Entity`, and a write to read-only state (such as the counters) with `403 Forbidden`.

### 10.6. Inject a Broadcast Storm

```bash
curl -s -X POST \
  -H 'Content-Type: application/yang-data+json' \
  http://127.0.0.1:8080/api/simulate/l2-storm \
  -d '{"port":"eth0","packets":5000}'
```

The endpoint answers `202 Accepted` with `{"status":"ok","port":"eth0","packets":5000}`. The injected frames move the interface counters of `eth0` and the other member ports, and a rate above the storm threshold raises a `TypeAlarmRaised` event (§9.2).

### 10.7. Walk the FDB over SNMP

```bash
snmpwalk -v2c -c public 127.0.0.1:1161 1.3.6.1.2.1.17.4.3.1.2
1.3.6.1.2.1.17.4.3.1.2.2.0.0.0.0.2 = INTEGER: 3
```

The community is fixed to `public` and the agent listens on the configured `snmp.port` (`configs/default.yaml` sets 1161). With `snmp.port: 161`, the standard port, the same command becomes:

```bash
snmpwalk -v2c -c public 127.0.0.1:161 1.3.6.1.2.1.17.4.3.1.2
```
