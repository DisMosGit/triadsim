# L2.md

**Project:** TriadSim — Lightweight Telecom Equipment Simulator  
**Protocols:** IEEE 802.1Q (VLAN), IEEE 802.1ad (QinQ), IEEE 802.1D/w (STP/RSTP), IEEE 802.1AB (LLDP)  
**Transport:** Layer 2 Ethernet  
**Data Encoding:** YANG (`sim-l2-switching` module), SNMP MIB objects

---

## 1. Introduction

The Layer 2 (L2) forwarding plane of TriadSim models the behavior of a VLAN-aware bridge as defined by IEEE 802.1Q. This document describes the supported L2 features: VLAN tagging (802.1Q), stacked VLANs (QinQ, IEEE 802.1ad), the MAC forwarding database (filtering database), a simplified Spanning Tree Protocol (STP/RSTP), Link Layer Discovery Protocol (LLDP), interface counters, and the corresponding MIB objects exposed via SNMP.

TriadSim does not implement a full data-plane forwarding ASIC. Instead, it models the **management-plane state** of an L2 bridge, allowing external management systems (NMS, SDN controllers) to read and configure VLAN membership, query the MAC table, observe STP port states, and monitor LLDP neighbor information. The L2 model is embedded in the `sim-l2-switching` YANG module and is accessible through all three northbound interfaces: SNMP, NETCONF, and RESTCONF.

## 2. IEEE 802.1Q — VLAN Tagging

### 2.1. Overview

IEEE 802.1Q defines the operation of VLAN-aware Bridges that support Virtual Local Area Networks. A VLAN is a logical partition of a Layer 2 network, identified by a 12-bit VLAN Identifier (VID). The standard specifies how the MAC Service is supported by Virtual Bridged Local Area Networks, the principles of operation of those networks, and the operation of VLAN-aware Bridges, including management, protocols, and algorithms.

TriadSim models VLANs as list entries under the `sim-l2-switching:vlans` container. Each VLAN entry has an `id` (VID, 1–4094), a `name`, and a set of member ports with tagging behavior.

### 2.2. VLAN Tag Format

An 802.1Q VLAN tag is inserted into the Ethernet frame header between the Source MAC Address and the EtherType/Length field. The tag header contains:

| Field | Size | Description |
|---|---|---|
| TPID | 16 bits | Tag Protocol Identifier (0x8100) |
| PCP | 3 bits | Priority Code Point (802.1p) |
| DEI | 1 bit | Drop Eligible Indicator |
| VID | 12 bits | VLAN Identifier (1–4094) |

The VLAN Identifier is a 12-bit field specifying the VLAN to which the frame belongs. All values except 0x000 and 0xFFF may be used as VLAN identifiers, allowing up to 4,094 VLANs.

### 2.3. Port VLAN Modes

Each bridge port operates in one of the following modes:

| Mode | Description |
|---|---|
| **Access** | Frames are untagged. The port is assigned to a single VLAN (PVID). |
| **Trunk** | Frames are tagged. The port carries multiple VLANs. |
| **Hybrid** | Frames may be tagged or untagged, depending on VLAN configuration. |

### 2.4. TriadSim VLAN Model

```go
type VLAN struct {
    ID          uint16   `path:"id" json:"id"`                     // 1-4094
    Name        string   `path:"name" json:"name"`
    Description string   `path:"description,omitempty" json:"description,omitempty"`
    Ports       []VLANPort `path:"ports/port" json:"ports"`
}

type VLANPort struct {
    Port     string `path:"port" json:"port"`         // e.g., "eth0", "radio0"
    Mode     string `path:"mode" json:"mode"`         // "access", "trunk", "hybrid"
    PVID     uint16 `path:"pvid" json:"pvid"`         // Port VLAN ID
    Tagged   bool   `path:"tagged" json:"tagged"`     // Tagged or untagged egress
}
```

## 3. IEEE 802.1ad — QinQ (Provider Bridging)

### 3.1. Overview

IEEE 802.1ad (Provider Bridges) is an amendment to IEEE 802.1Q that defines the architecture and bridge protocols for stacked VLANs, commonly known as Q-in-Q or Provider Bridging. The core idea is to provide separate instances of the MAC service to multiple independent users (customers) of a Bridged Local Area Network without requiring cooperation among the users, and with a minimum of cooperation between the users and the provider of the MAC service.

In QinQ operation, two VLAN tags are added to each customer Ethernet packet: the inner VLAN tag is customer-assigned (C-TAG), and the outer VLAN tag (S-TAG) corresponds to the carrier's assignment of a tunnel in which customer traffic is carried.

### 3.2. Frame Format

```
+----------+----------+----------+----------+----------+----------+
| Dest MAC | Src MAC  | S-TAG    | C-TAG    | Type/Len | Payload  |
| (6 bytes)| (6 bytes)| (4 bytes)| (4 bytes)| (2 bytes)|          |
+----------+----------+----------+----------+----------+----------+
```

| Tag | TPID | Purpose |
|---|---|---|
| **S-TAG** (Service Tag) | 0x88A8 | Provider-assigned; identifies the service instance |
| **C-TAG** (Customer Tag) | 0x8100 | Customer-assigned; identifies the customer VLAN |

### 3.3. TriadSim QinQ Model

TriadSim models QinQ encapsulation at the port level. A port configured with `qinq: true` will push an S-TAG on ingress and pop it on egress:

```go
type PortQinQ struct {
    Enabled     bool   `path:"enabled" json:"enabled"`
    STagVID     uint16 `path:"s-tag-vid" json:"s-tag-vid"`     // Outer tag
    CTagHandling string `path:"c-tag-handling" json:"c-tag-handling"` // "push", "pop", "transparent"
}
```

### 3.4. SNMP Mapping

QinQ-related objects are exposed under the Q-BRIDGE-MIB (RFC 4363) subtree, specifically the `dot1qVlan` and `dot1qTp` groups. The Q-BRIDGE-MIB module is used for managing Virtual Bridged Local Area Networks as defined by IEEE 802.1Q-2003.

## 4. MAC Forwarding Database (Filtering Database)

### 4.1. Overview

A MAC bridge maintains a Forwarding Database (FDB), also called the Filtering Database in IEEE 802.1D, to map destination MAC addresses to bridge ports. The bridge builds the FDB by means of a learning process, in which it associates the source MAC address of each incoming packet with the port on which the packet was received.

The FDB supports both dynamic entries (learned automatically) and static entries (configured by management). The IEEE 802.1D standard suggests an aging parameter with a default value of 300 seconds and a range of 10.0 to 10⁶ seconds.

### 4.2. FDB Entry Format

| Field | Description |
|---|---|
| `mac-address` | 48-bit MAC address (unicast) |
| `vlan-id` | VLAN ID (0 = no VLAN) |
| `port` | Bridge port number |
| `type` | `dynamic` or `static` |
| `age` | Time since last seen (for dynamic entries) |

### 4.3. TriadSim MAC Table Model

```go
type MACEntry struct {
    MAC       string `path:"mac-address" json:"mac-address"`
    VLAN      uint16 `path:"vlan-id" json:"vlan-id"`
    Port      uint32 `path:"port" json:"port"`
    Type      string `path:"type" json:"type"`             // "dynamic", "static"
    Age       uint32 `path:"age" json:"age"`               // seconds
    Permanent bool   `path:"permanent" json:"permanent"`
}

type MACTable struct {
    Entries       []MACEntry `path:"entry" json:"entry"`
    AgingTime     uint32     `path:"aging-time" json:"aging-time"`         // default 300
    MaxEntries    uint32     `path:"max-entries" json:"max-entries"`
    CurrentCount  uint32     `path:"current-count" json:"current-count"`
}
```

### 4.4. Aging Mechanism

TriadSim implements a simplified aging mechanism:

- Each dynamic entry has a timestamp of last activity.
- A background goroutine scans the table every 10 seconds.
- Entries exceeding `aging-time` are removed.
- Static entries are never aged out.

The default aging time is 300 seconds, configurable via the `aging-time` leaf.

### 4.5. CLI Example — Clear MAC Table


Or via RESTCONF RPC:

## 5. STP / RSTP (Simplified)

### 5.1. Overview

The Spanning Tree Protocol (STP, IEEE 802.1D) and its rapid variant (RSTP, IEEE 802.1w) prevent loops in bridged networks by electing a root bridge and placing redundant ports in a blocking or discarding state. RSTP is an improvement on the original STP standard, 802.1D, which allows faster convergence.

TriadSim implements a **simplified STP/RSTP state machine** that models port roles and port states without executing the full BPDU exchange protocol. The state machine is event-driven: port roles and states are configured or injected via the management plane, and the simulator publishes state changes to the EventBus.

### 5.2. Port Roles

RSTP defines the following port roles:

| Role | Description |
|---|---|
| **Root** | The port closest to the root bridge (forwarding) |
| **Designated** | The port providing the best path to the root for a LAN segment (forwarding) |
| **Alternate** | A backup port for the root port (discarding) |
| **Backup** | A backup port for a designated port (discarding) |

### 5.3. Port States

RSTP consolidates the five STP states (disabled, blocking, listening, learning, forwarding) into three states:

| State | Description | Learning | Forwarding |
|---|---|---|---|
| **Discarding** | Port does not forward or learn; combines STP’s disabled, blocking, and listening states | No | No |
| **Learning** | Port learns MAC addresses but does not forward | Yes | No |
| **Forwarding** | Port learns and forwards | Yes | Yes |

### 5.4. TriadSim STP Model

```go
type STPPort struct {
    Port       string `path:"port" json:"port"`
    Role       string `path:"role" json:"role"`         // "root", "designated", "alternate", "backup"
    State      string `path:"state" json:"state"`       // "discarding", "learning", "forwarding"
    Priority   uint8  `path:"priority" json:"priority"` // Port priority (0-240, step 16)
    PathCost   uint32 `path:"path-cost" json:"path-cost"`
    EdgePort   bool   `path:"edge-port" json:"edge-port"` // Edge/access port
}

type STPState struct {
    Enabled       bool       `path:"enabled" json:"enabled"`
    Protocol      string     `path:"protocol" json:"protocol"`           // "stp", "rstp"
    BridgePriority uint16    `path:"bridge-priority" json:"bridge-priority"` // 0-61440
    BridgeAddress string     `path:"bridge-address" json:"bridge-address"`   // MAC
    RootID        string     `path:"root-id" json:"root-id"`
    RootCost      uint32     `path:"root-cost" json:"root-cost"`
    Ports         []STPPort  `path:"ports/port" json:"ports"`
}
```

### 5.5. Simulated State Transitions

TriadSim allows the operator to inject STP events through the simulation API:

| Event | Effect |
|---|---|
| `TopologyChange` | Recalculate port roles (simulated) |
| `LinkDown` | Set port state to `discarding` |
| `LinkUp` | Transition port to `learning`, then `forwarding` |
| `ForceRoot` | Make the local bridge the root bridge |

### 5.6. SNMP Mapping — dot1dStp

STP objects are exposed through the `dot1dStp` subtree from BRIDGE-MIB (RFC 4188):

| MIB Object | OID | Description |
|---|---|---|
| `dot1dStpProtocolSpecification` | `1.3.6.1.2.1.17.2.1` | STP version |
| `dot1dStpPriority` | `1.3.6.1.2.1.17.2.2` | Bridge priority |
| `dot1dStpBridgeAddress` | `1.3.6.1.2.1.17.2.5` | Bridge MAC address |
| `dot1dStpPortState` | `1.3.6.1.2.1.17.2.15.1.3` | Port state per port |

## 6. LLDP (IEEE 802.1AB)

### 6.1. Overview

The Link Layer Discovery Protocol (LLDP), specified in IEEE 802.1AB, allows stations attached to an IEEE 802 LAN to advertise their identity, capabilities, and neighbors to other stations on the same LAN. LLDP is a one-way protocol: stations transmit LLDP Data Units (LLDPDUs) periodically and do not solicit responses.

TriadSim implements LLDP as a **management-plane model**: it maintains a local LLDP configuration and a table of remote neighbors, but does not generate or parse LLDP frames on the wire. Neighbor information can be injected via the simulation API or learned from a real LLDP implementation if integrated.

### 6.2. LLDPDU Structure

An LLDPDU consists of a sequence of Type-Length-Value (TLV) elements. Mandatory TLVs include:

| TLV | Type | Description |
|---|---|---|
| **Chassis ID** | 1 | Identifier of the chassis (MAC, IP, etc.) |
| **Port ID** | 2 | Identifier of the port |
| **Time To Live** | 3 | TTL in seconds (default 120) |
| **Port Description** | 4 | Description of the port |
| **System Name** | 5 | Assigned name of the system |
| **System Description** | 6 | Description of the system |
| **System Capabilities** | 7 | Bridge, router, repeater, etc. |

### 6.3. TriadSim LLDP Model

```go
type LLDPConfig struct {
    Enabled         bool   `path:"enabled" json:"enabled"`
    TxInterval      uint32 `path:"tx-interval" json:"tx-interval"`       // default 30s
    TxHoldMultiplier uint32 `path:"tx-hold-multiplier" json:"tx-hold-multiplier"` // default 4
    ReinitDelay     uint32 `path:"reinit-delay" json:"reinit-delay"`     // default 2s
    TxDelay         uint32 `path:"tx-delay" json:"tx-delay"`             // default 2s
    ChassisID       string `path:"chassis-id" json:"chassis-id"`
    SystemName      string `path:"system-name" json:"system-name"`
    SystemDescription string `path:"system-description" json:"system-description"`
}

type LLDPNeighbor struct {
    Port            string `path:"port" json:"port"`
    ChassisID       string `path:"chassis-id" json:"chassis-id"`
    PortID          string `path:"port-id" json:"port-id"`
    SystemName      string `path:"system-name" json:"system-name"`
    SystemDescription string `path:"system-description" json:"system-description"`
    TTL             uint32 `path:"ttl" json:"ttl"`

}
```

## 7. Interface Counters

### 7.1. Overview

TriadSim maintains per-interface counters as defined in the IF-MIB (RFC 2863). Counters are 32-bit or 64-bit and are reset on counter discontinuity events.

### 7.2. Supported Counters

| Counter | MIB Object | Type | Description |
|---|---|---|---|
| `ifInOctets` | `1.3.6.1.2.1.2.2.1.10` | Counter32 | Total octets received |
| `ifOutOctets` | `1.3.6.1.2.1.2.2.1.16` | Counter32 | Total octets transmitted |
| `ifInUcastPkts` | `1.3.6.1.2.1.2.2.1.11` | Counter32 | Unicast packets received |
| `ifOutUcastPkts` | `1.3.6.1.2.1.2.2.1.17` | Counter32 | Unicast packets transmitted |
| `ifInErrors` | `1.3.6.1.2.1.2.2.1.14` | Counter32 | Inbound errors |
| `ifOutErrors` | `1.3.6.1.2.1.2.2.1.20` | Counter32 | Outbound errors |
| `ifInDiscards` | `1.3.6.1.2.1.2.2.1.13` | Counter32 | Inbound discards |
| `ifOutDiscards` | `1.3.6.1.2.1.2.2.1.19` | Counter32 | Outbound discards |
| `ifHCInOctets` | `1.3.6.1.2.1.31.1.1.1.6` | Counter64 | 64-bit high-capacity octets in |
| `ifHCOutOctets` | `1.3.6.1.2.1.31.1.1.1.10` | Counter64 | 64-bit high-capacity octets out |

The IF-MIB defines that discontinuities in counter values can occur at re-initialization of the management system, and at other times as indicated by the value of `ifCounterDiscontinuityTime`.

### 7.3. TriadSim Counter Model

```go
type InterfaceCounters struct {
    InOctets    uint64 `path:"in-octets" json:"in-octets"`
    OutOctets   uint64 `path:"out-octets" json:"out-octets"`
    InUcastPkts uint64 `path:"in-ucast-pkts" json:"in-ucast-pkts"`
    OutUcastPkts uint64 `path:"out-ucast-pkts" json:"out-ucast-pkts"`
    InErrors    uint32 `path:"in-errors" json:"in-errors"`
    OutErrors   uint32 `path:"out-errors" json:"out-errors"`
    InDiscards  uint32 `path:"in-discards" json:"in-discards"`
    OutDiscards uint32 `path:"out-discards" json:"out-discards"`
}
```

## 9. Simulator Implementation

### 9.1. Go Package Structure

```
internal/l2/
├── vlan.go          # VLAN model and management
├── qinq.go          # QinQ encapsulation model
├── mac_table.go     # MAC forwarding database
├── stp.go           # STP/RSTP state machine (simplified)
├── lldp.go          # LLDP configuration and neighbor table
├── counters.go      # Interface counters
└── mib_map.go       # OID to model path mapping
```

> **Implemented model (Phase 1.2).** The managed objects of this domain landed early in
> `internal/model/l2.go`: `Interface`, `InterfaceCounters`, `VLAN`, `VLANPort`, `MACEntry`,
> `STPState`, `STPPort` and `LLDPNeighbor`, each with `Validate()`. The MAC-table and LLDP
> *containers* (`MACTable` with `aging-time`, `LLDPConfig`) arrive with the domain logic in
> Phase 4; the per-entry and per-neighbour types and their tags are already frozen.

### 9.2. Event Integration

| Event Type | Payload | Consumers |
|---|---|---|
| `VLANCreated` | `{vlan-id, name}` | SNMP trap, NETCONF notification, Prometheus |
| `VLANDeleted` | `{vlan-id}` | SNMP trap, NETCONF notification |
| `MACLearned` | `{mac, vlan, port}` | Prometheus (debug) |
| `MACAged` | `{mac, vlan, port}` | Prometheus (debug) |
| `STPPortStateChanged` | `{port, oldState, newState}` | SNMP trap, NETCONF notification |
| `LLDPNeighborAdded` | `{port, chassisID}` | SNMP trap |
| `LLDPNeighborRemoved` | `{port, chassisID}` | SNMP trap |
